# 演示与技术讨论

本项目定位为校招/初级 Agent 应用开发的工程作品。它可以展示 Agent 控制流、工具执行、故障恢复、检索和评测的具体实现；不代表字节跳动的官方录用标准，也不保证岗位匹配或录用。

## 10 分钟演示

1. 在 Studio 打开真实 OSS 任务，说明源码来自固定父提交，问题来自上游 issue/修复记录。
2. 展示自己的 `AgentRuntime`：模型返回单步 JSON，框架保存 pending 并执行 Docker 工具。
3. 展示检索引用和上下文事件，指出版本、行号、估算预算及原始观察保存位置。
4. 展示修改 diff、模型实际执行的命令、固定测试结果和独立隐藏 oracle 报告。现有公开测试原本通过并不代表问题不存在。
5. 运行 `scripts/check_forge_control.py`，解释响应丢失后的结果复用、参数冲突与旧租约拒绝。
6. 说明 100 任务队列与 2 个真实执行槽位的区别，展示实测报告而非宣传性吞吐数字。

## 应该能回答的问题

| 问题 | 代码与讨论点 |
|---|---|
| 为什么不直接调用完整 Coding CLI？ | `forge/runtime.py` 持有停止条件、工具边界、反馈循环和预算；CLI 桥接只是当前没有 API key 的决策入口 |
| 如何防止模型伪造“测试通过”？ | 任务固定独立 suite 版本；只读挂载测试、检查保护文件和实际测试计数；接受时核对当前策略和候选哈希，不相信 stdout 或 finish 声明 |
| 数据库提交后工具成功，但进程崩溃怎么办？ | 区分已记录结果与不确定结果，复用 call ID，不确定状态禁止自动重放 |
| 能不能保证 exactly-once？ | 不能跨 PostgreSQL/Docker 原子提交；解释操作日志与副作用间的故障窗口 |
| 如何避免长上下文失控？ | 有界窗口、工具组原子保留、外置产物、确定性摘要、累积预算；说明估算与真实 tokenizer 差异 |
| 为什么用 BM25 而非向量检索？ | 无外部 API、可解释引用、成本低；现有小型消融不能证明 hybrid 胜过纯 BM25 |
| 100 并发是怎么测的？ | 101 个并发提交、100 个唯一租约；与实际模型并发和容器并发分开计量 |
| 换一台 worker，原始工具输出还在吗？ | 新输出存入服务端 PostgreSQL，checkpoint 只持有受限预览与引用；新 worker 用当前租约从 API 读取。旧本地文件缺失不能凭摘要恢复；跨物理主机验证仍待补 |
| 如何继续提升？ | 更多未泄露真实任务、直接 API provider 实测、产物 retention / GC 和真实多机恢复验证、磁盘配额、故障注入覆盖、依赖镜像管理 |

## Bad case：现象、根因、处理与证据

以下区分三种证据：真实模型任务、真实 API/PostgreSQL/Docker 故障注入、使用脚本或 mock 的自动化测试。脚本证明执行协议，不证明模型一定能修好代码。只有明确的故障被修复或拒绝，才能说该场景已有处理；预算、隔离和人工审核不能保证所有任务成功。

### 1. 测试全绿，却引入兼容性回归

**真实发生：** cachetools 首次候选通过 63 项测试和 36 个子测试，但新增 `__class__` 属性把 descriptor 伪装成函数，导致 `mock` / `inspect` 读取不存在的 `__code__`。额外三项兼容性检查全部失败。这是模型产出代码的缺陷，不是 Forge 自身的业务代码缺陷。

**怎么处理：** 拒绝该候选，固定原 hidden 的成绩，另建 post-hoc 回归检查。先证明父版本和真实上游参考版本均通过这些检查，再将失败复现反馈给 Forge。后续源码用真实绑定方法替代类型伪装。完整修复链经过四个任务，最后一个任务还经历一次显式恢复；最终综合 87 passed / 36 subtests，兼容性 3 passed。不能讲成一次自主修复成功，也不能把新增的已知回归检查称为盲测。

**追问“隐藏测试都过了为什么还审查”：** 有限测试不是完整规格；隐藏测试覆盖原问题，额外审查揭示另一种兼容风险。测试成绩、代码审核与人工接受是不同关卡。

证据：[三方对照与全部尝试](../benchmarks/cachetools-autospec/post_hoc_review/REVIEW.md)、[最终补丁](../benchmarks/example-patches/cachetools-reviewed.patch)。

### 2. 模型写的新测试本身就是错的

**真实发生：** 第三次 cachetools 任务修好了源码，却把位置参数和关键字参数形成的两个缓存键当成同一个，新增测试有 6 项失败。

**怎么处理：** 不直接改源码去迎合模型断言；把相同新测试分别放到父版本和上游参考版本执行，两边同样失败，由此定位错误规格。第四次任务只修正这一新增测试中的断言，保留中间执行计数和缓存命中覆盖；上游原测试和第一次新增测试逐字不变。

**追问“是不是为了通过测试而改测试”：** 这里修改的是模型自己引入的错误测试，有两个独立对照支持；不是删测试、skip 或削弱上游用例。源码未改变，位置参数和关键字参数各自的缓存命中仍有实际执行覆盖。

证据：[验证记录](VALIDATION.md)、[结构化对照报告](../benchmarks/forge-run-summary.json) 的 `forge-cachetools-memory-retry-frozen-and-test-review.json` 和 `forge-cachetools-test-repair-change-review.json`。

### 3. 模型反复读代码，耗尽预算仍没有补丁

**真实发生：** 一次 follow-up 完成 21 次模型调用，已报告输入 / 输出 token 为 360392 / 2555，候选文件完全未变。排查发现工具动作中的 summary 没有进入后续上下文，模型的工作笔记丢失。这是 Forge 运行时自身被修复的缺陷。

**怎么处理：** 将 summary 保留在工具交换中，并保存最多 2000 字符工作笔记；作为不可信 user 内容纳入下一轮相同上下文预算，随检查点恢复。还设置有界历史、工具调用与观察成组裁剪、相同参数且相同结果的循环检测，以及步数、时间和累计 usage 限制。

**解决到什么程度：** 笔记传递和恢复机制已修，不能宣称模型从此不会绕圈。加笔记后的真实重试仍耗尽预算；没有受控消融证明总体成功率提高。循环检测能识别机械重复，不能可靠识别所有换一种问法的语义重复。

证据：[runtime 测试](../tests/test_forge_runtime.py) 的 `test_working_notes_survive_compaction_and_recovery`；[context 测试](../tests/test_forge_context.py) 的 `test_repeated_calls_are_blocked_only_when_observation_is_also_unchanged`、`test_alternating_observation_cycle_is_detected_with_a_bounded_window`。

### 4. 最后一次调用超预算，却还准备修改文件

**怎么处理：** 收到模型响应后先持久化 usage，再检查累计上限，超限时不派发该动作。恢复沿用保存的步数、修复次数与绝对截止时间，不能通过 resume 清零预算。

**追问“350k 是严格费用上限吗”：** 不是。模型调用已经发生，最后一次调用可以越过已报告 token 阈值；超额后停止工具和后续调用。失败、非法响应或中断可能没有返回可用 usage，不能当作零成本。没有供应商计费接口证据，也没有把 token 换算成费用。

证据：[runtime 测试](../tests/test_forge_runtime.py) 的 `test_over_budget_model_response_is_saved_but_cannot_mutate`、`test_step_budget_survives_resume`、`test_exhausted_repair_budget_cannot_be_reset_by_resume`、`test_persisted_deadline_blocks_resumed_pending_effect`。

### 5. 文件已经改了，但 HTTP 响应丢失，重试会不会改两次

**怎么处理：** 先 CAS 保存 pending call，再提交数据库操作意图，再执行外部操作并保存结果。恢复使用同一个 call ID；已提交结果直接复用，同 ID 不同参数返回 409，旧租约返回 409。真实故障注入里修改计数保持 1；自有循环恢复的缓存标记为 `[false, true, false]`，分别对应首次修改、恢复复用、固定测试。

**追问“副作用完成了，但结果还没入库就宕机呢”：** PostgreSQL 与 Docker 没有跨系统原子事务，这个窗口不能判断成功与否。系统保留不确定状态并拒绝自动重放，要求检查工作区后另起 follow-up。不能承诺 exactly-once；当前优先避免重复副作用，代价是部分任务需要人工处理。

当前实机故障注入固定覆盖了已提交结果的丢应答；不确定状态有拒绝分支和运行时单测，但尚未系统注入每一种 Docker/数据库崩溃时序。控制脚本中丢响应后可能进入已完成分支，不能把它当作所有故障窗口都已实测。

证据：[实际控制检查](../scripts/check_forge_control.py)、[循环故障注入](../scripts/check_forge_recovery.py)、[恢复 API](../src/agent_backend/forge/api.py)。这些集成检查使用脚本决策，0 次模型调用。

### 6. 服务升级时 502，任务没有完成上报

**真实发生：** 第四个 cachetools 任务在 API 升级期间失败，完成上报也未成功，之后因租约超时标记失败。

**怎么处理：** 保存失败快照，核实操作表为空，服务恢复后显式 resume 原任务、原检查点和原预算，最终完成。观察脚本现在能容忍短暂 502/503/504，并重用保存的任务 ID。

**边界：** 这证明了停止后可显式恢复，不代表 worker 能自动跨过所有 API 故障或零停机部署。工具状态不确定、时间已过期、预算耗尽或项目版本推进都会拒绝直接恢复。

证据：[完整时间与恢复记录](VALIDATION.md)、[任务观察脚本](../scripts/check_forge_followup.py)。

### 7. 并发领取重复任务、旧结果覆盖新版本

**怎么处理：** PostgreSQL `FOR UPDATE SKIP LOCKED` 领取任务；按身份的 advisory lock 串行化队列准入；执行器行锁保护槽位容量。接受补丁时锁定项目并检查起始版本，仅推进不可变工作区指针。过期任务不能覆盖已经接受的新版本。

**验证：** 101 个并发提交，100 个入队、1 个 429；20 个脚本执行器分配 100 个唯一租约。版本冲突、身份隔离和完成幂等另有真实控制检查。

**边界：** 这是队列与领取验证，真实模型并发只测了 2 路；单次突发也不是长期 QPS 或 SLO。没有跨身份公平调度和生产容量结论。

证据：[队列检查](../scripts/check_coding_queue.py)、[版本与完整流程检查](../scripts/check_coding_flow.py)、[Coding API](../src/agent_backend/coding/api.py)。

### 8. 恶意路径、长输出、测试修改工作区

**怎么处理：** ZIP 解包前检查路径、数量、展开大小与文件类型；拒绝穿越、符号链接和敏感路径。文本替换要求匹配无歧义。工具限制输出与执行时间，超长观察外置并保留错误尾部；裁剪时不拆散调用和结果。测试在临时复制卷中执行，测试副作用不会污染待审补丁。容器无网络、非 root、有 CPU/内存/PID 限制，不挂宿主凭据和 Docker socket。

**边界：** Docker 不是恶意多租户的完整安全证明；持久卷没有磁盘硬配额。命令已进入 broker 后可能继续执行到超时，取消不会瞬间回滚文件或杀掉所有外部副作用。

证据：[沙箱测试](../tests/test_sandbox_helper.py) 的 `test_zip_paths_are_validated_before_extracting`、`test_archive_limits_and_path_conflicts_are_atomic`、`test_replace_text_requires_unambiguous_match`；[真实沙箱检查](../scripts/check_sandbox_live.py)；[长上下文测试](../tests/test_forge_context.py)。

### 9. 初始化中断，重试却把改后的代码当作修改前基线

**本轮复核发现并补修：** 原实现先提交 `workspace_ready=True`，再运行并记录基线。若中间崩溃，重试会直接返回工作区，基线证据缺失。不能简单拿当前文件补跑：当前文件可能已被修改，失败的父任务也可能恢复后继续变化。

**处理方式：** 为任务创建固定标识的初始快照，基线只对该快照执行；基线结果和 `workspace_ready` 一起提交。用单独的事务级 advisory lock 串行化同一任务的初始化，长时间测试期间不持 Task 行锁，允许心跳与取消继续执行。最后重新锁定 Task、刷新状态与租约，才发布准备完成。历史任务如果已经 ready 却缺失基线，明确拒绝伪造修改前证据。

**恢复边界：** 重试优先读取已冻结快照，即使原 seed 已消失也能使用相同初始内容。ZIP 存在不代表初始化完整，使用前还验证 Git 基线；半初始化卷明确拒绝，不拿后来变化的源文件重建基线。该分支有单元回归，尚未通过真实 Docker 杀进程复现。

**取舍：** 初始快照需要额外持久存储；当前没有完整的快照保留期限和垃圾回收策略，不能声称资源永久不增长。

### 10. 完成和取消并发，较早的取消标志被忽略

**本轮复核发现并补修：** 原实现最后读取控制字段时未加锁，读取与写终态之间存在取消竞态；异常退出分支也需要同样保护。

**处理方式：** 外部 diff / 测试结果先放局部变量，避免 ORM 自动 flush 抢先写回。写最终状态前重新 `SELECT FOR UPDATE` 刷新记录，检查取消标志、当前状态和租约，再一起提交结果与事件。旧租约的迟到完成请求不能覆盖新租约。

**面试要讲清的顺序：** 取消先取得行锁并提交，后完成应看到取消；完成已经提交终态后再取消，则不会撤销已完成结果。这是事务顺序语义，不是让取消永远获胜，更不是立即终止远端 Docker 命令。

以上两项对应 [生命周期回归测试](../tests/test_coding_lifecycle.py) 和 [真实数据库并发检查](../scripts/check_coding_lifecycle.py)；实际执行结果见 [验证记录](VALIDATION.md)。

### 11. 检查点还在，原始观察却留在旧 worker

**发现的缺口：** 原实现把完整观察保存为 worker 本地文本，数据库 checkpoint 只保留预览与 URI。换一个没有这些文件的 worker，状态虽然能加载，`read_artifact` 却拿不到原文。重新读当前源码也不能还原历史命令输出。

**处理方式：** 新增服务端 PostgreSQL artifact 表，按 Task 与内容哈希寻址；所有读写验证 owner 和有效租约。原文不可覆盖，重复上传幂等；单项限制 1 MiB，每任务累计 16 MiB / 256 项，写入和配额检查使用同一 Task 行锁。worker 先提交原文，再发布 observation 事件及 checkpoint；API 在 checkpoint CAS 提交前核对引用存在且元数据一致。恢复后的 worker 不需要原 worker 文件，使用新租约经 API 分页读取。

**追问“上传成功，检查点没成功怎么办”：** 两次请求不是一个原子事务，可能留下未引用原文，但不会发布不可读的新 checkpoint。恢复仍依据旧 pending 和工具操作日志；不能因为产物哈希存在就认定未知副作用成功。上传应答丢失可按相同内容幂等重试。

**边界：** 旧本地文件仍在时可以校验迁移；数据已经丢失就明确返回 unavailable，无法凭哈希重建。现有功能回归覆盖独立客户端换租约、无旧目录读取、隔离和配额；真实 HTTP/PostgreSQL 探针只按其实际报告陈述，不等于已经验证多物理主机容灾。`ToolOperation.result` 和事件中仍可能保留重复内容，没有 retention / GC，也没有数据库灾备结论。

证据：[服务端原文 API](../src/agent_backend/forge/artifacts.py#L49)、[checkpoint 引用校验](../src/agent_backend/forge/artifacts.py#L93)、[worker 持久化顺序](../scripts/forge_worker.py#L53)、[功能回归](../tests/test_forge_artifacts.py)、[接口与恢复说明](ARTIFACTS.md)。

### 12. 改测试、改 pytest 配置，或者提交验收后的另一份代码

**旧设计为什么不够：** 冻结测试命令仍允许候选修改该命令加载的测试文件、conftest 或收集配置；只检查 exit 0 还可能把空测试或跳过测试记为成功。离线 benchmark 有独立 oracle，但原先普通任务没有这一机制。

**处理方式：** 独立验收包保存在服务端，任务固定 suite ID/digest，保护清单固定原文件哈希。运行器在私有容器只读挂载测试，使用镜像 pytest、固定参数及显式测试入口，忽略候选配置。进程成功、结构化报告、最少收集数与全部通过必须同时成立；skip、xfail、假 stdout、缺少报告、超时均不能通过。人工接受还会在锁内重算候选摘要并检查当前策略，防止验收后换内容或按旧标准合入。

**为什么策略升级后不直接重写旧任务：** 旧任务的基线、运行过程和完成结果属于原标准。悄悄换 pin 会破坏证据可追溯性，所以发布新策略后要求新建 follow-up。历史无 suite 的任务仍可审阅和下载，但不能新接受。修改保护文件也需要操作者明确更新标准。

**边界：** 这是仓库级绕过防护，候选 Python 与 pytest 仍共享解释器，不能承诺防恶意解释器篡改。隐藏测试不是永不泄漏的秘密；授权操作者也能发布弱标准。当前只支持受限 Python/pytest，插件、导入命名冲突和依赖不兼容会明确失败。

证据：[验收策略](ACCEPTANCE.md)、[API 回归](../scripts/check_acceptance.py)、[Docker 绕过检查](../scripts/check_acceptance_sandbox.py)、[历史坏候选与好候选三方对照](../scripts/check_acceptance_oss.py)。最后一项使用已经存在的真实模型产物，包含已披露的复审用例，不能宣传成新的盲测或本轮新模型修复。

| 提示注入 | 源码、工具结果和工作笔记标记为不可信；schema 和沙箱约束可执行能力 | 没有真实模型攻击集，不能声称提示注入已解决；需要代码注释/测试日志/检索结果攻击样本，并测泄露、越权和任务偏离 |
| 跨机器完整恢复与存储生命周期 | 新原文已在服务端 PostgreSQL，可凭当前租约经 API 读取；旧本地数据缺失仍不可恢复；没有 retention / GC | 做真实多物理主机、旧 worker 永久离线和数据库恢复验证；制定历史数据保留与清理策略，测长期容量 |
| 供应商故障与计费 | HTTP 错误有明确分类，非法动作拒绝执行；原生 HTTP provider 未做真实调用 | 有 key 后测 429、timeout、流控和重试幂等；对账 usage，不能把无回包当零成本 |
| 大规模模型吞吐 | 100 任务控制层验证；2 路真实模型运行 | 单独测多机模型任务、供应商额度、持续负载、队列等待时间与尾延迟 |

## 可以直接使用的两分钟回答

“有，最有代表性的不是 HTTP 报错，而是模型产出的补丁通过了原测试和隐藏测试，却破坏了 Python 的 introspection。我用父版本、参考修复和候选三方对照确认回归，反馈给自己的 Agent 循环继续修复，并保留预算耗尽和错误测试等失败。之后参照 SWE-bench 的独立评测思路，把普通任务也改为版本化验收包：测试只读挂载，保护原文件，接受时校验策略和候选哈希；不再把 stdout 或 exit 0 单独当作成功。工程侧，已提交工具结果的丢应答用同一个 call ID 恢复；结果未入库则拒绝重放，不承诺 exactly-once。长观察先存服务端，再发布 checkpoint 引用，新 worker 可用新租约取回原文。真实模型只测了两路并发，恶意解释器篡改、提示注入攻击集、多物理主机恢复和长期存储回收仍未完整验证。”

## 简历表述原则

可以写清实现和验证过的事实，例如：“实现 Coding Agent 的结构化决策循环、代码检索与上下文预算；设计带 CAS 检查点和工具调用去重的恢复协议，在双 API/PostgreSQL/Docker 环境验证 100 任务准入与唯一领取；使用冻结的开源历史 bug 和隐藏测试评估修复。”

模型任务数量、结果和耗时请引用 [验证记录](VALIDATION.md) 的实测值。不要写成“100 个真实 Agent 同时运行”“生产级恶意多租户隔离”“在 SWE-bench 达到某分数”，也不要把模型生成的代码包装成自己没有理解的技术能力。面试前应实际运行、改动并讲清上述故障窗口。
